## 3. 新发现的问题

### P0-1 客户端把布尔查询参数编码成 `True`，服务端只认小写 `true`

- **现象**：`Client.list_assets(confirmedCharacter=True)` 经 `urlencode` 变成 `True`，服务端直接返回 **HTTP 400** `confirmedCharacter 必须是 true 或 false`。
- **复现**：
  ```python
  c.list_assets(confirmedCharacter=True)          # → 400
  c.list_assets(confirmedCharacter='true')        # → 200（只能靠调用方手改）
  ```
- **影响**：服务端刚加的角色检索能力（`?characterWork=…&characterName=…&confirmedCharacter=…`）**从客户端几乎无法调用**——而这正是新工作流里"先查库内已确认角色参考"那一步要用的接口。
- **位置**：客户端 `skills/aigc-asset-upload/scripts/shelf_client.py` 的 `list_assets()`；服务端校验在 `server/src/index.js`（`confirmedCharacter` 只接受 `'true'`/`'false'` 字符串）。
- **建议**：客户端在拼接查询串前把所有布尔值转成小写字符串（`str(v).lower()`），并在 `asset-api.md` 里写明"布尔参数传字符串小写"。

### P0-2 同一条 reel 的不同字节版本会绕过 SHA-256 去重

- **现象**：Instagram `DactUk9Ayv3` 这条 reel：

  | | 库内条目 `80c35992` | 本轮下载的 VP9 原流 |
  | --- | --- | --- |
  | sha256 | `8aecab093e891fbf…` | `4836f3dfbf4c6302…` |
  | 字节数 | 2,975,365 | 2,975,365 |
  | 时长 | 14.248s | 14.248s |
  | sourceUrl | 同一条 | 同一条 |

  **字节数、时长、sourceUrl 全一致，只有哈希不同**（IG 侧同一条视频两次下发字节不一致）。`upload_one()` 的预检只查 `[交付副本 sha256, 原件 sha256]`，两个都不命中 → 会把同一段素材再传一条。
- **影响**：库里会多出一条几乎一样的素材，而网格里看起来是同一段视频。技能文档要求"宁可漏传，也不要在库里制造两条几乎一样的素材"，但**上传前的自动预检没有能力识别这种情况**。
- **建议**：上传前增加近重复预检——同 `sourceUrl`（归一化后）或同 folder 且时长 ±10% 即可判为已存在（服务端 `similarTo` 已有同款规则 `sameFolderAndDurationWithin10Percent` / `sameSourceUrl`，客户端直接复用即可）。命中时按"以库内那条为准"跳过并在结果里标注 `duplicate`。
- **附带**：这条规则的准确度依赖 sourceUrl 归一化，见 P1-5。

### P0-3 库内存量条目是站点原流，不是兼容副本，而"替换"没有可执行路径

- **现象**：
  - 库里那两条存的是 **VP9 / HEVC 原流**（2.8 MB / 2.5 MB），新流程交付的是 **H.264/yuv420p + AAC**（10.2 MB / 12.3 MB）。原流在 QuickTime 里播不了。
  - 技能文档写「这不会替换线上旧文件，若需要替换应另行处理」——但**没给"另行处理"的入口**：
    - `organize_assets.py` 只有 `--set-name` / `--set-tags`，没有替换文件的选项；
    - 服务端其实有 `POST /api/assets/:id/file`（+ `POST /api/assets/:id/file/finalize`）可替换文件，**技能层完全没有封装**。
- **影响**：存量条目无法平滑迁移到"兼容交付"策略；每条都要人肉走一遍 API。
- **建议**：给整理技能加 `--replace-file <本地路径>`（内部走 `POST /api/assets/:id/file` → finalize → 回读校验），并写进 SKILL.md 的"替换线上文件"章节。

### P1-4 整理技能写不了角色字段，新加的 `characterCandidates` 在存量素材上补不齐

- **现象**：`organize_assets.py apply` 只支持 `--set-name` / `--set-tags`；`characterName` / `characterCandidates` 只能绕过技能、直接 `PATCH /api/assets/:id/organize` 才能写入（本轮的汉库克与黑寡妇两条就是这样补的）。
- **影响**：库里 1390 条里 `characterCandidates` 非空只有 **2** 条，服务端新加的角色检索能力几乎无从命中；库里 929 条 `characterName` 为空，历史素材无法通过角色维度被检索到。
- **建议**：整理技能补 `--set-character-name` / `--set-character-candidates`（可从本地清单读候选），并在 `inspect` 的分类里把"缺角色字段"列出来。

### P1-5 `sourceUrl` 是精确匹配，同一条 reel 换个链接形态就查不到

- **现象**：服务端按 `a.source_url = $n` 精确比对，入库时保存的是用户给的**原样链接（含分享参数）**。实测同一条：

  | 查询 | 结果 |
  | --- | --- |
  | `?sourceUrl=…/p/DYz84ltxh5y/?mdxt=MXMwbzJlMjVsYTRsNQ==` | 1 条 ✓ |
  | `?sourceUrl=…/p/DYz84ltxh5y/`（去参数） | **0 条** |
  | `?sourceUrl=…/reels/DYz84ltxh5y/` | **0 条** |

- **规模**：全库 1390 条中 **115 条（8.3%）** 的 sourceUrl 带查询参数；Instagram 链接同时存在 `/p/`（160 条）、`/reels/`（36 条）、`/reel/`（单数）三种路径形态。
- **已存在的实例**：同一短码 `Da8aCVMqodX` 以 `/reels/` 和 `/reel/` 各存一条（`8a67a168` 与 `0748f039`，6.15s / 11.3s 两个不同片段，其中一条标题还是原始文件名 `instagram-reel-20260831153705`）。
- **影响**：P0-2 要求的"上传前按 sourceUrl 预检近重复"如果只做精确匹配就会漏判；同一 reel 在库里也可能出现多条不同形态的记录。
- **建议**：
  1. 存储前归一化：去查询参数、去尾斜杠、`/p/` `/reel/` `/reels/` 统一为一种形式（同时在 `sourceUrl` 保留用户原始链接，或新增 `sourceUrlNormalized` 字段）；
  2. 匹配前用归一化值比对；
  3. 客户端保留原始分享链接（用于回溯），但预检一律用归一化值。

## 5. 顺带确认可用的新能力（供后续调用参考）

- **单条详情**：`GET /api/assets/:id` → `{"asset":{...}}`，含 `sha256`、`sizeBytes`、`durationSeconds`、`createdAt`、`mediaMetadata`、`streamUrl` / `directUrl` / `thumbUrl`。
- **列表分页**：`GET /api/assets` → `{assets, total, limit, offset, hasMore}`；支持 `ids`、`q`（名称/来源/角色名/标签模糊）、`folder`、`tag`、`sourceUrl`、`characterName`、`characterWork`、`confirmedCharacter`、`duration_min` / `duration_max`、`since`、`similarTo`。
- **元数据校验**：写操作带 `X-AIGC-Metadata-Policy: curated-v1` → 标题 ≤32 字、禁 `·` 与 `.`、标签 3–5 个；失败返回 400 与字段级错误（`{"error":"素材元数据校验失败","fields":[…]}`）。
- **角色候选**：`characterCandidates[{work,name,evidence,confidence,confirmed}]`（≤5 个），配合 `?characterWork=…&confirmedCharacter=true` 可检索"已确认的同角色参考素材"。
- **并发保护**：`/organize` 的 `before` 字段是改前快照，不一致返回 **409**——**必须先读当前值再写**。本轮第一次写备注时把 `before.note` 填成空串（真实值是默认文案「新上传素材，等待补充备注。」）就被 409 拦下。
- **媒体元数据**：新上传素材服务端会自行 ffprobe 写入 `mediaMetadata`（`width/height/videoCodec/pixelFormat/audioCodecs`），旧素材为 `{}`。

## 6. 运维备忘（踩过的坑）

1. **布尔查询参数在客户端是小写问题**：`confirmedCharacter=true` 生效、`True` 报 400。
2. **`before` 快照要先读当前值**：写备注/改名/改标签前先 `get_asset()` 取真实值，否则 409。
3. **`sourceUrl` 查询是精确匹配**：想确认"这条视频是否已在库"，要用与服务端完全一致的字符串（带参数）。
4. **静音段要区分来源**：本轮用 `import_video.py verify` 单独校验下载原件，确认 6.155–7.582s 静音是原片自带（原件与交付副本的 mean/max 完全一致），不是转码引入。**技术校验通过 ≠ 已人工确认听感**。
5. **原流与交付副本要分开汇报体积**：不要用 MB 大小判断清晰度，转码是 CRF 18 有损且会变大。
6. **venv 里没有 pytest**：技能自测用 `python -m unittest discover -s <tests目录> -p <文件名>`。
