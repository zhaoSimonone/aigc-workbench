# 百度网盘上传速度排查：问题与结论

> 面向高阶模型的排查材料。目标是判断"0.8 MB/s 到底是哪一环造成的"，以及提速方案是否成立。
>
> 排查时间：2026-10-12　环境：macOS（Darwin 25.3.0 arm64）
> 相关代码：`skills/baidu-netdisk-archive/scripts/netdisk_sync.py`

> **高阶复核**：本文的原始实验保留。修订后的瓶颈判断和实施优先级见 `docs/百度网盘上传速度排查-高阶复核与优化方案.md`。重点修正：不能把 4 MB/s 直接归因到 20 MHz Wi-Fi；整批任务的第一优化项不是分片大小，而是连接复用、文件级并发和分片重试。
>
---

## 0. 一句话结论（待确认）

上传流量**不经过工作台服务器**，是 `Mac → 百度网盘` 直连。观测到的 ~4 MB/s 聚合天花板**大概率来自本机 Wi-Fi 链路（5GHz 但仅 20MHz 信道）或家用宽带上行**，而非百度接口限速。但脚本当前只跑出 0.8–1.0 MB/s，**浪费了约 75% 的可用带宽**，这部分是可以修的。

两项结论都还缺一次决定性验证，见 §6。

## 2. 流量路径（已确认，非瓶颈）

脚本只访问两个域名：

```python
API        = "https://pan.baidu.com"
UPLOAD_API = "https://d.pcs.baidu.com/rest/2.0/pcs/superfile2"
```

工作台 Node 服务只做 `GET /api/list` 读取目录元数据（每次几百字节），**完全不参与文件字节传输**。停掉批量任务后单独跑剖析脚本，速度与批量时一致——若流量经由服务器，单独跑会明显更快。

## 3. 实测数据

### 3.1 单文件分阶段耗时（908视频，9.3 MB，3 分片）

| 阶段 | 耗时 |
|---|---|
| ① 计算全部分片 MD5（本地读盘+hash） | 0.02 s |
| ② precreate（一次 API 往返） | 0.53 s |
| ③ 分片上传 3 片 | 3.96 s → **2.35 MB/s**（纯传输，不含 sleep） |

### 3.2 逐分片速率（68.9 MB 文件，18 片，每片 4 MB）

```
第 1片  1.44s = 2.78 MB/s      第10片 1.24s = 3.24 MB/s
第 2片  1.27s = 3.15 MB/s      第11片 3.41s = 1.17 MB/s
第 5片  1.51s = 2.65 MB/s      第14片 1.23s = 3.26 MB/s
第 8片  2.89s = 1.38 MB/s      第17片 1.37s = 2.93 MB/s
第18片  1.53s = 0.61 MB/s（异常）
```

平均约 **2.7 MB/s**，波动大且**无单调衰减**——不是长连接被持续限速的特征，更像网络抖动。

### 3.3 分片大小对照实验（同一时刻、相同条件）

| 分片 | 请求数 | 耗时 | 端到端吞吐 | 单请求延迟 |
|---|---|---|---|---|
| **4 MB**（当前） | 9 | 33.51 s | **0.98 MB/s** | 3723 ms |
| **8 MB** | 5 | 15.33 s | **2.14 MB/s** | 3065 ms |
| 16 MB | 3 | 16.10 s | 2.04 MB/s | 5365 ms |
| 32 MB | 2 | 23.73 s | 1.38 MB/s | 11867 ms |

**8 MB 是拐点，比 4 MB 快 2.2 倍。** 4 MB 分片时每片 3.7 s，而同样数据量下 8 MB 分片每片 3.1 s——固定往返开销在 4 MB 粒度下摊薄了有效带宽。

### 3.4 并发对照实验（决定性）

| 并发连接 | 聚合吞吐 | 单请求延迟 |
|---|---|---|
| 1 | 2.48 MB/s | 1615 ms |
| 2 | 2.45 MB/s | 1431 / 3267 ms |
| 4 | 3.73 MB/s | 2642 / 3144 / 3344 / 4289 ms |
| 8 | **4.05 MB/s** | 3403 … 7909 ms |

**关键**：8 条连接只有 1.6 倍提升，并趋于饱和。若百度按单连接限速，8 连接应接近 8 倍。这说明存在一个**总带宽天花板 ≈ 4 MB/s（≈32 Mbps）**。

## 4. 已排除的原因

| 假设 | 排除依据 |
|---|---|
| 工作台服务器带宽 | 流量直连百度，服务器只读目录元数据 |
| VPN 绕道海外 | 默认路由 `default → en0` 走物理网卡；无 `0.0.0.0/1` 拆分路由；无系统 HTTP/HTTPS 代理；无本地代理端口监听（7890/7891/6152/1087/8888/10809/1080/9090）；ping `pan.baidu.com` **30 ms**、`d.pcs.baidu.com` **54 ms**（绕道海外会 200–400 ms）。6 个 utun 接口虽 UP，但属分流模式，百度判 DIRECT |
| 百度 QPS 限流 | 百度开放平台的限制是 QPS，表现为报错/请求被拒，不会是平滑的带宽封顶；且逐片速率忽高忽低无稳定压制 |
| 本地磁盘 I/O | MD5 全量计算 9.3 MB 仅 0.02 s |
| 网盘容量 | 可用 11.76 TB，本次占 0.16% |
| 每文件 API 往返开销 | 是真实开销（见 §5），但只是叠加因素，不是主因 |

## 5. 脚本侧确认的浪费

| 开销 | 量级 | 评价 |
|---|---|---|
| `BLOCK_SIZE = 4 MB` 分片过碎 | 使有效吞吐从 ~2.1 掉到 ~1.0 MB/s | **最大单项浪费**，约 2 倍 |
| 每文件 `precreate`(0.53 s) + `create` 各一次往返 | 3801 文件 × ~1 s ≈ **63 分钟纯等待**，与文件大小无关 | 对小文件多的目录影响显著 |
| 每分片 `time.sleep(0.15)` | 18 片 ≈ 2.7 s / 68.9 MB | 约 4%，是防限流的保险 |
| 完全串行 | 并发实验显示可提升 ~1.6 倍 | 有效但受总带宽封顶 |

## 6. 尚未确认的关键问题（希望重点分析）

### Q1：4 MB/s 天花板到底来自哪里？

**目前只是推断，没有直接测到上行带宽。** 下行测速全部失败：

| 测速源 | 结果 | 可用性 |
|---|---|---|
| `speed.cloudflare.com` | 1.15 MB/s | ❌ Cloudflare 在国内线路极差 |
| `mirrors.aliyun.com` | HTTP 302 / 0 字节 | ❌ 重定向目标不可达 |
| `mirrors.tuna/ustc` | HTTP 404 | ❌ 版本号已下线 |
| `registry.npmmirror.com` | 0.45 MB/s | ❌ 文件仅 ~1 MB，测不出带宽 |

已知的间接证据：

```
Wi-Fi: PHY Mode 802.11ax, Channel 52 (5GHz, 20MHz)
```

**5GHz 但只有 20MHz 信道**（现代路由器通常 40/80MHz），可利用频谱减半。叠加家用宽带上行通常仅 30–50 Mbps，32 Mbps 是合理结果。

**需要的验证**：在同一网络下用手机/其他设备跑测速工具看**上行**带宽，或把 5GHz 信道宽度改为 40/80 MHz 后重测 §3.4 的并发实验。若并发峰值上到 6–8 MB/s，则此前确为 Wi-Fi 链路限制。

### Q2：分片大小实验的 2.2 倍提升是否可信？

每档只跑了一次，存在网络抖动污染（对照 §3.2 的波动幅度很大）。**需要重复 3 次取中位数**再决定是否把默认值从 4 MB 改成 8 MB。

### Q3：改大 `BLOCK_SIZE` 是否削弱校验保证？

`SKILL.md` 明确记录："每个 4MB 分片都用服务端回显的 MD5 逐片校验"，并标注"这些是实测结论，不要凭直觉改写"。改成 8 MB 后每片 MD5 校验依然执行、覆盖面不变，只是单个校验块变大。**理论上单个分片内静默损坏的检出边界从 4 MB 扩到 8 MB**。是否可接受？是否应保留 4 MB 默认、仅在大批量场景显式指定？

### Q4：并发是否还能更高？

8 并发已饱和（4.05 MB/s）。若 Q1 确认瓶颈是 Wi-Fi/宽带，则并发无更多空间；若瓶颈实际在百度侧的每连接 QoS，则可能仍有空间。**当前数据不足以区分。**

## 7. 拟定方案（尚未实施，等确认）

保持默认行为完全不变，仅新增可选参数：

```
--chunk-size   默认 4MB（与文档一致）
--concurrency  默认 1（保持串行）
```

批量上传时显式使用 `--chunk-size 8M --concurrency 4`。需同步改动：远端目录缓存加锁、进度输出加锁、分片按需流式读取（不整文件载入内存）。

预期：0.8–1.0 MB/s → 3–3.5 MB/s，19.8 GB 从约 7 小时降到约 1.7 小时。

`time.sleep(0.15)` 建议保留（4% 收益 vs 失去防限流保护）。

## 8. 排查过程中发现并已修复的独立 Bug

`netdisk_sync.py quota` 命令的 `free` 字段对会员账号不可靠：

| 参数 | total | used | free |
|---|---|---|---|
| `checkfree=1` | 12293 GB ✓ | 249.96 GB ✓ | **100.00 GB** ✗ |
| 不带参数 | 12293 GB ✓ | 249.96 GB ✓ | **0 GB** ✗ |

`free` 返回的是**普通用户基础免费空间**（固定 100 GB 上限），不含 SVIP 权益。已改为一律用 `total - used` 计算，并在偏差超 1 GB 时显式标注接口值不可信。

真实可用空间 **11.76 TB**（此前基于错误的 100 GB 得出"空间充足"，结论侥幸正确但依据错误）。
