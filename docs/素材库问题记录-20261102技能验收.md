## 3. 新发现的问题

### P0-1 客户端把布尔查询参数编码成 `True`，服务端只认小写 `true`

- **现象**：`Client.list_assets(confirmedCharacter=True)` 经 `urlencode` 变成 `True`，服务端直接返回 **HTTP 400** `confirmedCharacter 必须是 true 或 false`。
- **复现**：
  ```python
  c.list_assets(confirmedCharacter=True)          # → 400
  c.list_assets(confirmedCharacter='true')        # → 200（只能靠调用方手改）
  ```
- **影响**：服务端刚加的角色检索能力（`?characterWork=…&characterName=…&confirmedCharacter=…`）**从客户端几乎无法调用**——而这正是新工作流里"先查库内已确认角色参考"那一步要用的接口。
- **位置**：客户端 `skills/aigc-asset-upload/scripts/shelf_client.py` 的 `list_assets()`；服务端校验在 `server/src/index.js`（`confirmedCharacter` 只接受 `'true'`/`'false'` 字符串）。
- **建议**：客户端在拼接查询串前把所有布尔值转成小写字符串（`str(v).lower()`），并在 `asset-api.md` 里写明"布尔参数传字符串小写"。

### P0-2 同一条 reel 的不同字节版本会绕过 SHA-256 去重

- **现象**：Instagram `DactUk9Ayv3` 这条 reel：

  | | 库内条目 `80c35992` | 本轮下载的 VP9 原流 |
  | --- | --- | --- |
  | sha256 | `8aecab093e891fbf…` | `4836f3dfbf4c6302…` |
  | 字节数 | 2,975,365 | 2,975,365 |
  | 时长 | 14.248s | 14.248s |
  | sourceUrl | 同一条 | 同一条 |

  **字节数、时长、sourceUrl 全一致，只有哈希不同**（IG 侧同一条视频两次下发字节不一致）。`upload_one()` 的预检只查 `[交付副本 sha256, 原件 sha256]`，两个都不命中 → 会把同一段素材再传一条。
- **影响**：库里会多出一条几乎一样的素材，而网格里看起来是同一段视频。技能文档要求"宁可漏传，也不要在库里制造两条几乎一样的素材"，但**上传前的自动预检没有能力识别这种情况**。
- **建议**：上传前增加近重复预检——同 `sourceUrl`（归一化后）或同 folder 且时长 ±10% 即可判为已存在（服务端 `similarTo` 已有同款规则 `sameFolderAndDurationWithin10Percent` / `sameSourceUrl`，客户端直接复用即可）。命中时按"以库内那条为准"跳过并在结果里标注 `duplicate`。
- **附带**：这条规则的准确度依赖 sourceUrl 归一化，见 P1-5。

### P0-3 库内存量条目是站点原流，不是兼容副本，而"替换"没有可执行路径

- **现象**：
  - 库里那两条存的是 **VP9 / HEVC 原流**（2.8 MB / 2.5 MB），新流程交付的是 **H.264/yuv420p + AAC**（10.2 MB / 12.3 MB）。原流在 QuickTime 里播不了。
  - 技能文档写「这不会替换线上旧文件，若需要替换应另行处理」——但**没给"另行处理"的入口**：
    - `organize_assets.py` 只有 `--set-name` / `--set-tags`，没有替换文件的选项；
    - 服务端其实有 `POST /api/assets/:id/file`（+ `POST /api/assets/:id/file/finalize`）可替换文件，**技能层完全没有封装**。
- **影响**：存量条目无法平滑迁移到"兼容交付"策略；每条都要人肉走一遍 API。
- **建议**：给整理技能加 `--replace-file <本地路径>`（内部走 `POST /api/assets/:id/file` → finalize → 回读校验），并写进 SKILL.md 的"替换线上文件"章节。

### P1-4 整理技能写不了角色字段，新加的 `characterCandidates` 在存量素材上补不齐

- **现象**：`organize_assets.py apply` 只支持 `--set-name` / `--set-tags`；`characterName` / `characterCandidates` 只能绕过技能、直接 `PATCH /api/assets/:id/organize` 才能写入（本轮的汉库克与黑寡妇两条就是这样补的）。
- **影响**：库里 1390 条里 `characterCandidates` 非空只有 **2** 条，服务端新加的角色检索能力几乎无从命中；库里 929 条 `characterName` 为空，历史素材无法通过角色维度被检索到。
- **建议**：整理技能补 `--set-character-name` / `--set-character-candidates`（可从本地清单读候选），并在 `inspect` 的分类里把"缺角色字段"列出来。

### P1-5 `sourceUrl` 是精确匹配，同一条 reel 换个链接形态就查不到

- **现象**：服务端按 `a.source_url = $n` 精确比对，入库时保存的是用户给的**原样链接（含分享参数）**。实测同一条：

  | 查询 | 结果 |
  | --- | --- |
  | `?sourceUrl=…/p/DYz84ltxh5y/?mdxt=MXMwbzJlMjVsYTRsNQ==` | 1 条 ✓ |
  | `?sourceUrl=…/p/DYz84ltxh5y/`（去参数） | **0 条** |
  | `?sourceUrl=…/reels/DYz84ltxh5y/` | **0 条** |

- **规模**：全库 1390 条中 **115 条（8.3%）** 的 sourceUrl 带查询参数；Instagram 链接同时存在 `/p/`（160 条）、`/reels/`（36 条）、`/reel/`（单数）三种路径形态。
- **已存在的实例**：同一短码 `Da8aCVMqodX` 以 `/reels/` 和 `/reel/` 各存一条（`8a67a168` 与 `0748f039`，6.15s / 11.3s 两个不同片段，其中一条标题还是原始文件名 `instagram-reel-20260831153705`）。
- **影响**：P0-2 要求的"上传前按 sourceUrl 预检近重复"如果只做精确匹配就会漏判；同一 reel 在库里也可能出现多条不同形态的记录。
- **建议**：
  1. 存储前归一化：去查询参数、去尾斜杠、`/p/` `/reel/` `/reels/` 统一为一种形式（同时在 `sourceUrl` 保留用户原始链接，或新增 `sourceUrlNormalized` 字段）；
  2. 匹配前用归一化值比对；
  3. 客户端保留原始分享链接（用于回溯），但预检一律用归一化值。

### P1-6 「同作品既有命名先例」被误套到同作品的不同角色上

- **现象**：上传技能要求"同一作品与同一角色优先沿用库内已核实的写法"。实操中把"同一作品"当成了充分条件：本轮 `DfPSNWHugSv`（原帖文案 `フリーレンのコスプレ`，片头贴图为芙莉莲立绘）明明 cos 的是**芙莉莲**，却因为库里已有两条 `葬送的芙莉莲-尤贝尔-…` 而被标成了尤贝尔，用户当场纠正。
- **为什么先例不能套用**：《葬送的芙莉莲》里的**尤贝尔**是绿发、紫瞳、黑色连衣裙配项圈/手套/腰带（萌娘百科「发色 绿发、瞳色 紫瞳」）；**芙莉莲**是银发双马尾、长精灵耳、白金镶边黑白横条战斗服。两人造型完全不同，不能因同属一部作品就互换。
- **影响**：标题、标签、`characterName`、`characterCandidates` 四个字段同时错标；`characterCandidates.confirmed=true` 是流程状态而非事实，错了之后反而让错误结论以"已核实"的形态入库，按 `characterName=尤贝尔` 检索会召回一条不是尤贝尔的素材。
- **建议**：
  1. 先例的适用条件收紧为"**同一作品 + 同一角色**"，且必须让贴图/文案与角色造型同时吻合；
  2. 角色候选的 `evidence` 写清区分性特征（发色、瞳色、标志性服装），便于事后复核而不是只留一句"吻合"；
  3. 角色名与作品名同名的条目（cos 主角）单独约定命名格式，避免"作品名-角色名"出现 `葬送的芙莉莲-芙莉莲` 这类重复，并防止主角条目的命名先例污染其他角色条目。

### P1-7 `characterCandidates` 的 `work` 强制非空，"待识别"条目在无已知作品时无处可填

- **现象**：服务端 `parseCharacterCandidates` 要求每个候选的 `work` / `name` / `evidence` 都是**非空**字符串（`server/src/index.js:365`）。库里既有的"待识别"候选都挂在某个已确认角色名下，`work` 填的是该作品名：
  - `e8818b6c` → `{"name":"待识别","work":"Re零",…}`
  - `6b54ad22` → `{"name":"待识别","work":"海贼王",…}`
  当一条视频**没有任何可确认作品**（纯穿搭、万圣节妆造、趋势造型）时，"待识别"候选没有作品可指认，`work` 只能填空串 → 整条上传被 **400** 拒绝（`角色候选应为最多 5 项的数组，含 work/name/evidence/confidence(0–1)/confirmed`）。
- **本轮实测**：`DeuDvkMtYqr`（万圣节僵尸妆，无贴图、无文案角色线索）首次上传即因 `work: ""` 失败；把 `work` 填为占位值 `待识别` 后上传成功，`characterName` 仍留空、`confirmed:false`，与库内既有做法一致。
- **影响**：纯穿搭/妆造类素材只要带了"待识别"候选就会 100% 上传失败；技能文档没有说明这个非空约束，也没有给出"无已知作品"时的填法。
- **建议**：
  1. 明确 `work` 允许填写占位值（如 `待识别`），用于"作品与角色都未确认"的候选；
  2. 或放宽为 `work` 可为空字符串，仅要求 `name` / `evidence` 非空；
  3. 技能文档在"候选记录在 `characterCandidates`"处补一句该约束与占位写法。

### P1-8 Instagram 域名被 DNS 污染，下载链路整体断在网络层而非账号层

- **现象**：2026-11-05 批次 11 条 Instagram 链接首次下载时，`yt-dlp` 对**每一条**都报 `curl: (28) Connection timed out after 25001 milliseconds`，`import_video.py prepare` 最终 11/11 失败、`errors` 全满。
- **根因不是登录态失效**：本机 `dig www.instagram.com` 解析到 `199.59.148.7`（Twitter IP 段）与 `108.160.165.212`（Dropbox IP 段），而 `dig @8.8.8.8` 返回 `z-p42-instagram.c10r.instagram.com → 57.144.204.34`（Meta 段）。即**系统 DNS 把 Instagram 域名污染到了无关厂商的 IP**；直连污染 IP 超时，`--resolve` 到正确的 `57.144.204.34` 也在 TLS 阶段被拒（code=000）。同机 `example.com` 直连 200，说明不是整体断网。
- **可用绕行**：本机已有代理在 `127.0.0.1:7890`（系统 `HTTPEnable=1`），经该代理访问 `www.instagram.com` 返回 200、耗时 1.8s。`import_video.py prepare` 支持 `--proxy`，加上 `--proxy http://127.0.0.1:7890` 后 11 条全部下载并通过校验。
- **影响**：失败信息是「连接超时」，容易被误判成"账号掉登录态"或"链接失效"而反复重试或重新登录；同时 `yt-dlp --print description` 抓文案走的也是同一路径，会一起超时。
- **建议**：
  1. 技能在批量下载前先做一次连通性探测（`www.instagram.com` 直连 + 代理各测一次），超阈值时直接提示"疑似 DNS 污染，请指定 `--proxy`"；
  2. 把"用 `dig @8.8.8.8` 对比系统 DNS 结果"写进下载失败的排查清单；
  3. 支持从环境变量或配置读取默认代理，避免每批手动传参。

## 5. 顺带确认可用的新能力（供后续调用参考）

- **单条详情**：`GET /api/assets/:id` → `{"asset":{...}}`，含 `sha256`、`sizeBytes`、`durationSeconds`、`createdAt`、`mediaMetadata`、`streamUrl` / `directUrl` / `thumbUrl`。
- **列表分页**：`GET /api/assets` → `{assets, total, limit, offset, hasMore}`；支持 `ids`、`q`（名称/来源/角色名/标签模糊）、`folder`、`tag`、`sourceUrl`、`characterName`、`characterWork`、`confirmedCharacter`、`duration_min` / `duration_max`、`since`、`similarTo`。
- **元数据校验**：写操作带 `X-AIGC-Metadata-Policy: curated-v1` → 标题 ≤32 字、禁 `·` 与 `.`、标签 3–5 个；失败返回 400 与字段级错误（`{"error":"素材元数据校验失败","fields":[…]}`）。
- **角色候选**：`characterCandidates[{work,name,evidence,confidence,confirmed}]`（≤5 个），配合 `?characterWork=…&confirmedCharacter=true` 可检索"已确认的同角色参考素材"。
- **并发保护**：`/organize` 的 `before` 字段是改前快照，不一致返回 **409**——**必须先读当前值再写**。本轮第一次写备注时把 `before.note` 填成空串（真实值是默认文案「新上传素材，等待补充备注。」）就被 409 拦下。
- **媒体元数据**：新上传素材服务端会自行 ffprobe 写入 `mediaMetadata`（`width/height/videoCodec/pixelFormat/audioCodecs`），旧素材为 `{}`。

## 6. 运维备忘（踩过的坑）

1. **布尔查询参数在客户端是小写问题**：`confirmedCharacter=true` 生效、`True` 报 400。
2. **`before` 快照要先读当前值**：写备注/改名/改标签前先 `get_asset()` 取真实值，否则 409。
3. **`sourceUrl` 查询是精确匹配**：想确认"这条视频是否已在库"，要用与服务端完全一致的字符串（带参数）。
4. **静音段要区分来源**：本轮用 `import_video.py verify` 单独校验下载原件，确认 6.155–7.582s 静音是原片自带（原件与交付副本的 mean/max 完全一致），不是转码引入。**技术校验通过 ≠ 已人工确认听感**。
5. **原流与交付副本要分开汇报体积**：不要用 MB 大小判断清晰度，转码是 CRF 18 有损且会变大。
6. **venv 里没有 pytest**：技能自测用 `python -m unittest discover -s <tests目录> -p <文件名>`。
7. **命名先例要连角色一起对**：「同一作品与同一角色沿用库内已核实写法」里的"同一角色"不能省略。同作品的另一个角色造型完全不同（尤贝尔绿发黑裙 vs 芙莉莲银发白金战斗服），照抄即错标。`characterCandidates.confirmed=true` 只是流程状态，不是事实——结论要能被贴图和造型推翻，也要能被用户纠正推翻。
8. **回读用技能自带的 `shelf_client`**：会话文件是 `{"aigc_session": "…"}` 形式的 JSON，不是 Netscape cookie jar，`curl -b <file>` 会得到"未登录"。用 `aigc-asset-upload/scripts/shelf_client.py` 的 `Client` 发请求即可。

**结论**：微信视频号已打通端到端链路——`https://weixin.qq.com/sph/AFYKmQzHZ0` 已下载、识别并上传到「灵感收集」，素材 ID `43630772-f373-41a0-b6fa-f4521208e85d`，`source=视频号`，回读 7 项字段全一致；灵感收集总数 584 → 585。技能侧新增 weixin 平台适配（`identify` / `download_weixin` / `source` 映射 / `weixin/<id>` 目录），并补 3 个单测，现有 27 个单测全通过。

### 8.1 视频号解析的两条路线

25. **视频号链接形态**：`https://weixin.qq.com/sph/<id>` 是短链，301 跳到 `https://channels.weixin.qq.com/finder-preview/pages/sph?id=<id>`（JS 驱动）。页面 JS 再调 `POST /finder-preview/api/feed/get_feed_info`。
26. **无头捷径只能拿到元数据，拿不到视频**：`POST https://channels.weixin.qq.com/finder-preview/api/feed/get_feed_info`，body `{"baseReq":{"generalToken":""},"shortUri":"<id>"}`，**不需要任何 cookie** 就能返回 errCode 0，含作者昵称、文案、封面、`sceneInfo.dynamicExportId`。但用 `exportId` 变体取视频直链时返回 `errMsg.type=2「此内容暂时无法播放」`——它需要 `generalToken`。
27. **元宝接口是另一条路，但它要用户凭据**：`POST https://yuanbao.tencent.com/api/weixin/get_parse_result`，body `{"type":"video_channel_url","url":"<sph>","scene":1}`，返回 `playable_url`（含 `token`/`eid`），再用 `token`+`eid` 调 `get_feed_info` 就能拿到 `videoUrl`。**实测不带 cookie 一律 401「未知错误」**，带齐上游那套 `x-agentid`/`x-device-id` 等头部也不行。cookie 属用户资产，**不主动索取**，因此正式链路走下面的页面路线。
28. **页面路线（本次采用）不依赖任何用户凭据**：本机跑 `wx_video_download`（上游 `ltaoo/wx_channels_download`）作为本地代理，它把系统代理指向自己的 HTTPS 端口并 MITM `channels.weixin.qq.com`，在返回的 HTML 里注入 `channels.ws.js`/`getFeedInfo.js`；微信的视频号页面一旦加载，注入脚本就回连代理的 `/ws/channels`，`GET /api/scraper/platform/status` 的 `wxchannels:page` 随即变为 available，此时 `/api/scraper/fetch` 能拿到含 `videoUrl` 的完整 feed。

### 8.2 必须踩准的操作姿势

29. **要在会话里打开链接，不能在搜索框里搜**：把链接发到「文件传输助手」再点那条消息气泡，微信才会用**带登录态的 webview** 打开视频号页面；只在搜索框里输入短链，出现的「访问网页」卡片属于微信搜索面板，它**不会**建立视频号页面连接（`wxchannels:page` 始终 unavailable，代理日志里连 `channels.weixin.qq.com` 都不会出现）。判据是代理日志：页面连上时会出现 `channels.weixin.qq.com` 命中并随后有 `/ws/channels` 握手。
30. **微信自绘 UI 的 AX 树几乎是空的**（AX 树里只有 3 个窗口按钮），`System Events` 的元素点击与 `click at` 全部无效；**但 AX 键盘输入可用**（`keystroke` 能往搜索框打字、能在会话里发消息）。真正能用的是**自写 CGEventPost 鼠标事件**：`CGEventSource(stateID: .hidSystemState)` + `CGEvent(mouseEventSource:mouseType:.leftMouseDown/.leftMouseUp)`，编译成小二进制即可，光标会真实移动。
31. **之前判定"点击无效"其实是被一个未关闭的「打开」sheet 挡住了**：微信窗口上弹过文件选择面板（AX 树里是 `AXSheet desc=打开`，带「取消/打开」按钮），它吃掉焦点并覆盖在窗口上方，坐标点击全被它吞掉。**先确认没有模态面板再动鼠标**，用 AX 按 `AXPress` 关掉，或 `key code 53`（Esc）。
32. **代理二进制按架构选**：上游 `bin/wx_video_download` 是 arm64-only，本机是 Intel x86_64（i7-7660U），必须下官方发布页的 `wx_video_download_v261106_darwin_x86_64.zip`，Intel 原生可跑。
33. **代理会改系统代理、装 MITM 根证书，还会被看门狗顶回来**：本机 mihomo（awcloud 内核）占 7890，`com.awcloud.watchdog` 每轮校验并把系统代理强制改回 7890，必须先 `launchctl bootout` 卸载，采集结束再 `launchctl bootstrap` 装回，并把所有网络服务的 web/secure/socks 代理恢复成 `127.0.0.1:7890`。
34. **视频号媒体是加密流**：`finder.video.qq.com/.../stodownload` 直链 GET 回来是随机字节（无 ftyp 头，`file` 报 `data`），**不能**当普通 mp4 直链保存。必须走代理的解密下载管线：`POST /api/v1/download_task/create`，body `{"objects":[{"platform":"wxchannels","content":<fetch 的 output.result 原始 feed>,"build_from_fetch":true,"filename":"media.mp4","config":{"spec":"<fileFormat>"},"auto_start":true}]}`，再轮询 `GET /api/v1/download_task/detail?id=`，`status==5` 即完成，`files[].file_path` 是解密后的 mp4。
35. **清晰度要自己挑**：代理默认按 WeChat 的 `levelOrder` 选「最高级」，本例给的是 `xWT111`（720×1280、码率 1490）；1080p 变体是 `xWT102`（1080×1920、**HEVC**）。技能侧改为按**分辨率面积再比码率**选最大变体，再交给既有的交付策略转成 H.264 yuv420p/AAC 副本，HEVC 原件保留在 `sourcePath`。

### 8.5 自建页面操作 vs computer use 插件（实测对照）

47. **computer use 在微信上拿不到任何内容元素**：插件的 `computer_app_state` 返回 120 个 AX 节点，**全是菜单栏**（Apple/微信/文件/编辑/显示/窗口/帮助）加 3 个窗口按钮——聊天列表、气泡、输入框一个都没有。这与自建 AX dump 的结论一致：**微信是自绘 UI，两条路线在微信上都只能走坐标**，computer use 的语义点击/元素 token 优势在这里完全用不上。
48. **computer use 的后台点击对微信无效，前台点击有效**：`computer_click` 走 background 时只投递不移动硬件指针（工具自报 "the hardware pointer was not moved"），微信自绘 UI 收不到，实测点击后视频号面板纹丝不动；改 `delivery_mode:"foreground"` 后立刻生效（工具自动把截图坐标 1568×817 换算成屏幕点 677,241）。**自写 CGEvent 之所以后台就够，是因为它会真实移动指针**——事件落在指针下的前台窗口。
49. **成本与延迟差一个量级**：computer use 每次观察要吐 ~7–8K token 的 AX 树（第二次观察还因 1000ms 预算超时截断）外加一张 1568×817 截图，坐标还得我看着截图估；颜色定位器 2.4 秒返回两个数字，连续三次结果完全相同，且自带窗口矩形动态读取与「先激活微信再截图」的保护。
50. **各自的适用面**：computer use 强在有标准 AX 语义的地方（原生菜单、对话框、带标签的按钮），且能「看懂」颜色定位器认不出的东西（比如别人发的白色气泡、图片/卡片消息）；颜色定位器强在重复定位同一个像素不变式。**结论：对微信这类自绘 UI，两者可靠性同档，都得靠坐标，但自建方案在确定性、成本、后台可用性上更优；换到标准界面则 computer use 明显更强。**

### 8.6 气泡定位器补齐「对方气泡」（备忘 51–55）

51. **对方气泡不是纯白，是冷调浅灰**。实测本机 WeChat 4.x for macOS 浅色主题的四个关键色值：自己发的气泡 ≈`#95EC69`（按色相判定，浅绿非标准值）、**对方发的气泡 `#EEEEF0`（238,238,240，带一点蓝）**、聊天面板底色 `#FAFAFA`（250,250,250）、底部输入框 `#FFFFFF`（255,255,255）。原先「三个通道 ≥252 即为白」的判据在本机微信上**根本匹配不到对方气泡**——它比面板底色还暗；同时又会被输入框和右侧面板的大片纯白带偏（曾在腾讯新闻会话误命中 `x[432..666] y[600..612] w=235 px=60` 的假带）。
52. **定位器重写**（`skills/video-inspiration-import/scripts/weixin_bubble.py`，仓库内自带，不再依赖 `~/.minimax/tools/clicker/find_bubble.py`）：`classify()` 改为三色类——`green`（色相）、`received`（冷调浅灰，范围 232–249 且蓝通道高于红通道）、`white`（纯白，兼容旧主题的对方气泡）。`--kind white` 现在指「对方气泡」（received 或 white 皆可），`auto` 优先级为 `green > received > white`。对方气泡头像在左，点击点取气泡右 1/4；自己发的气泡头像在右，取左 1/4。
53. **三重过滤**：稀疏反锯齿像素会被 min/max 撑成假宽带，靠**密度 ≥0.45** 滤掉；底部输入框靠 `--pane-bottom`（默认窗口高 −150）**几何排除**；宽度上限由 55% 放宽到 80%——长链接列表消息实测占面板 72%（391/580），55% 会把真实对方气泡一起误杀。
54. **实机验证**：「文件传输助手」会话中 `--kind green` 与 `--kind auto` 均返回 `613 242 green`，裁图确认落在 `AVhvcBzuyB` 链接文字上；同一会话 `--kind white` 正确报「未找到」而不是误点输入框。切到 Simonone 会话（有一条对方发来的长链接消息，背景实测 `(238,238,240)`）后 `--kind white` 返回 `661 120 received`，该带 391×87、密度 0.77，落在气泡内且避开左侧头像。
55. **教训：「颜色不变式」必须先实测这台机器上该 UI 的真实色值**，不能照抄经典配色或凭肉眼判断（238,238,240 看起来就是白）。另外绿色气泡与聊天列表选中行同色，仍需靠面板 x 范围 + 取最下方来区分。

## 10. 下载后自动关闭视频号页面（备忘 61–65）
