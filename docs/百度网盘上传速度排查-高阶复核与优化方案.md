# 百度网盘上传速度排查：高阶复核与优化方案

> 复核时间：2026-10-12 21:30（Asia/Shanghai）
> 原始报告：`docs/百度网盘上传速度排查-分析报告.md`
> 相关代码：`skills/baidu-netdisk-archive/scripts/netdisk_sync.py`
>
> 原始实验数据有价值，但“4 MB 分片是最大浪费”“4 MB/s 主要由 20 MHz Wi-Fi 导致”两项结论需要修正。

## 1. 修订后的结论

### 1.1 4 MB/s 聚合上限基本是当前网络出口/到百度链路的上限，但不能归因到「20 MHz Wi-Fi」

复核时重新读取当前 Wi-Fi 状态：

```text
PHY Mode: 802.11ax
Channel: 52 (5GHz, 20MHz)
Signal / Noise: -52 dBm / -101 dBm
Transmit Rate: 206 Mbps
MCS Index: 11
```

20 MHz 不是理想配置，但当前 PHY 发送速率仍有 206 Mbps，信噪比约 49 dB，不能解释业务流量为什么停在 32 Mbps。

随后使用 macOS 自带命令只测上行：

```bash
networkQuality -I en0 -d -M 30 -c
```

结果：

```text
ul_throughput = 42,389,388 bit/s ≈ 40.4 Mib/s ≈ 5.05 MB/s
ul_flows = 12
```

百度 8 并发实测峰值约 4.05 MB/s，相当于通用上行测速的约 80%。因此：

- 聚合 4 MB/s 已接近当前网络出口能提供的实际上行能力；
- 瓶颈可能位于企业/家用出口整形、运营商上行、到百度 PCS 的路由或百度接入节点，不能仅凭信道宽度归因到 Wi-Fi；
- 把脚本优化到 3.5–4.2 MB/s 是合理目标；在当前网络下长期达到 6–8 MB/s 不现实，除非换网络后 `networkQuality` 的上行也同步提高。

### 1.2 0.86 MB/s 的主要损失不是 4 MB 分片，而是「大量小文件 + 全串行 + 每次请求重新握手」

重新扫描当前 `/Users/simon/Desktop/AIGC` 下匹配 `^\d+视频$` 的目录。内容可能比原报告生成时多了少量文件：

| 指标 | 当前值 |

| 总大小 | 19.96 GiB |
| 中位文件大小 | **1.60 MiB** |
| 平均文件大小 | 5.18 MiB |

约 75% 文件使用 4 MiB 分片时本来就只有一片。把分片从 4 MiB 调到 8 MiB，对这些文件不会减少分片请求，也不会省掉每文件 precreate/create。

按当前文件集估算：

| 分片大小 | 分片请求数 | 相比 4 MiB 减少 | `sleep(0.15)` 总和 |
|---|---:|---:|---:|
| 4 MiB | 7799 | — | 19.5 分钟 |

| 32 MiB | 4200 | 46.1% | 10.5 分钟 |

3942 个文件还有约 7884 个固定的 precreate/create 控制请求。因此原报告基于一个 33 MB 文件得出的“4 MB 分片是最大单项浪费”，不能外推到整批任务。

整批任务应优先优化：

1. HTTP 连接复用；
2. 文件级并发；
3. 小文件上传路径；
4. 最后才是分片大小。

## 2. 当前代码中报告未覆盖的问题

### 2.1 P0：`urllib.request` 强制 `Connection: close`

当前 `_request()` 每次调用 `urllib.request.urlopen()`。Python 3.9 标准库 `AbstractHTTPHandler.do_open()` 会明确加入：

```python
headers["Connection"] = "close"
```

并在每个响应后关闭 socket。于是每个 precreate、每个分片、每个 create 都重新走 TCP/TLS 建连，不能 Keep-Alive。

当前实测 `d.pcs.baidu.com` 一次 TLS 建连约 0.22 秒。数千次请求累计后是明显开销，也会放大网络抖动。

建议：每个 worker 使用长生命周期 `requests.Session` 或等价连接池；连接池上限与全局并发一致。不要跨进程共享 Session，不要记录含 Token 的完整 URL。

### 2.2 P0：上传域名被固定为 `d.pcs.baidu.com`

当前代码：

```python
UPLOAD_API = "https://d.pcs.baidu.com/rest/2.0/pcs/superfile2"
```

百度当前文档要求预上传拿到 `uploadid` 后调用 `locateupload`，获取该任务的推荐上传域名，并明确说明不要在生产代码里固定上传域名。推荐结果有短有效期，可能包含多个 HTTPS/QUIC 节点。

这不保证速度必然翻倍，但它会影响接入节点和路由，是判断“百度限速还是网络限速”之前必须消除的变量。

注意：当前脚本使用能写 `/AIGC` 根目录的旧 `/api/precreate`、`/api/create` 契约；当前公开文档主要以 `/apps/{appname}` 为例。不要在同一个提交里盲目迁移整套控制接口。第一步只验证旧 uploadid 能否调用 locateupload、返回 host 能否继续完成 `/AIGC` 上传。

### 2.3 P0：数据分片没有网络重试

`call_retry()` 只覆盖 list/precreate/create。真正传数据的 `put_block()` 直接调用 `_request()`。网络闪断、TLS reset、HTTP 5xx 或 PCS 临时错误会直接让整个文件失败。

并发提高后失败概率会增加，因此必须增加分片级重试：

- 同一 `uploadid + partseq` 原地重试；
- 每次从同一 offset 重读该片；
- 指数退避并带少量 jitter；
- 最多 3–4 次；
- 每次仍校验服务端回显 MD5；
- 只有分片重试耗尽才判文件失败，不重传前面已成功的片。

### 2.4 P1：预上传返回的“需要上传分片”没有被利用

当前代码只判断旧字段 `return_1`。只要不是整文件秒传，就上传 `range(len(digests))` 的全部分片。

百度当前三步上传契约会返回需要上传的分片序号 `block_list`；官方 SDK也只上传该列表中的分片。应先记录一次旧 `/api/precreate` 的**去敏响应字段结构**：

- 如果旧响应有等价分片列表，只传缺失片；
- 如果没有，则保持全部上传；
- 不要未经验证直接把旧字段替换成新字段。

对全新视频收益可能较小，对重复片段、断点恢复和失败续传收益较大。

### 2.5 P1：8 MiB 对当前 SVIP 合法，但“校验变弱”不是正确担忧

百度当前规则：普通用户单片 4 MiB，会员最高 16 MiB，超级会员最高 32 MiB。当前账号是 SVIP6，8 MiB 在允许范围内，现有实验也表明服务端接受。

把 4 MiB 改成 8 MiB 后，每个字节仍被对应分片 MD5 覆盖。真正变化是：

- 分片失败时最多重传 8 MiB，而不是 4 MiB；
- 内存峰值和单请求持续时间增加；
- 网络抖动时单次失败代价更高。

所以应评估的是重传成本和超时概率，不是“校验覆盖变弱”。

### 2.6 P1：当前分片 multipart 会复制内存

`put_block()` 用 `header + data + trailer` 拼出完整 bytes，会额外复制一个分片。8 MiB × 并发 4 尚可接受；32 MiB × 并发 8 会明显增加内存。

第一阶段不必为了流式 multipart 过度重构，但应：

- 先限制全局并发；
- 每个 worker 独立打开文件或使用 `os.pread`；
- 不把整文件载入内存；
- 若未来用 16/32 MiB，再切流式 multipart。

## 3. 正确的优化优先级

### P0：先补可观测性

每个文件输出或写 JSONL：

- `list_ms / hash_ms / precreate_ms / locate_ms / upload_ms / create_ms`
- `file_bytes / chunk_size / chunks_total / chunks_requested / chunks_uploaded`
- `retry_count / errno / HTTP status`
- `effective_MBps`（整个文件）与 `payload_MBps`（仅分片）
- 实际上传 host（只记 host，不记带 Token 的 URL）

没有这些指标，无法判断 Keep-Alive、动态域名、并发分别贡献多少。

### P1：Session + 动态上传域名 + 分片重试

第一提交保持 `chunk=4 MiB`、`concurrency=1`，只改基础设施：

1. 长连接 Session；
2. precreate 后 locateupload；
3. 分片原地重试；
4. connect/read timeout；
5. 日志去敏；
6. 分阶段指标。

这一阶段单独测试，避免和并发混在一起后无法归因。

### P2：只做文件级并发，初始值 4

当前 74.6% 文件不超过 4 MiB。文件级并发可以同时隐藏多个文件的 precreate/create、单片上传等待和偶发慢连接。

第一版不要同时做“4 个文件 × 每文件 4 个分片”的嵌套并发：

- 一个全局 `ThreadPoolExecutor(max_workers=4)`；
- 每个文件内部串行上传分片；
- 每个 worker 独立 Session；
- 全局上传请求最多 4 个；
- 失败文件独立记录，其他任务继续；
- Ctrl-C 停止发新任务，并取消尚未开始的 future。

为避免目录创建竞态，增加串行规划阶段：

1. 收集本地文件和目标目录；
2. 串行 ensure/create 所有目录；
3. 串行或分目录读取远端文件名/size，形成不可变计划；
4. 只把确定要上传的文件交给并发池。

这样比给 `remote_cache` 到处加锁更简单，也避免两个 worker 同时创建同一目录而产生时间戳垃圾目录。

### P3：增加 8 MiB 可选档，不把它当主要提速手段

建议参数：

```text
--chunk-size 4M|8M|16M|32M
--concurrency 1..8
--profile safe|fast
```

建议配置：

| profile | chunk | file concurrency | 适用 |
|---|---:|---:|---|
| safe（默认） | 4 MiB | 1 | 保持兼容、普通用户 |
| fast（当前 SVIP） | 8 MiB | 4 | 当前批量任务 |

如果服务端返回分片大小超限（如 31364），必须整文件重新按 4 MiB 计算 block list 并重新 precreate，不能只把当前片切成 4 MiB 继续旧 uploadid。

### P4：评估小文件单步上传，但必须先做兼容性试验

百度当前提供“小文件一次请求完成上传和建文件”的接口。当前 74.6% 文件 ≤4 MiB，若当前应用权限和 `/AIGC` 路径允许，单步上传可能省掉每文件 precreate/create，是比改大分片更直接的优化。

但公开文档主要约束到 `/apps/{appname}`，而当前脚本写的是 `/AIGC` 根目录。因此它只能作为实验项：

- 用无敏感小文件在专用测试前缀验证；
- 核对落盘路径、覆盖/重名行为和删除清理；
- 不通过就放弃；
- 不要为了单步上传迁移正式目录。

### P5：固定 `sleep(0.15)` 改为可观测、可配置

不建议第一步直接删除：

- `safe` 保留 0.15 秒；
- `fast` 设为 0 或 0.03 秒；
- 出现频控/5xx/连接重置时由重试和全局退避接管；
- 并发模式若需限速，使用全局 rate limiter；多个 worker 各自 sleep 不能形成可靠的全局 QPS 保护。

## 4. 修订后的性能预期

当前通用上行约 5.05 MB/s，百度聚合已测到 4.05 MB/s。合理目标是把脚本从 0.86 MB/s 提高到接近已验证峰值：

| 阶段 | 预计整批有效吞吐 | 说明 |
|---|---:|---|
| 当前串行 | 0.8–1.0 MB/s | 已实测 |
| Session + 重试 + 推荐 host，串行 | 1.0–2.0 MB/s | 依赖服务器等待和 host 路由，需实测 |
| 再加文件并发 2 | 2.0–3.2 MB/s | 开始隐藏每文件控制请求 |
| 文件并发 4 | **3.2–4.2 MB/s** | 接近当前网络上限，推荐目标 |
| 并发 8 | 3.8–4.3 MB/s | 增益很小，失败率更高，不建议默认 |

19.8 GiB 在 3.2–4.0 MB/s 的纯传输时间约 1.4–1.8 小时。考虑 3942 个文件的控制请求、跳过判断和重试，实际建议按 **1.8–2.5 小时**规划，不承诺 1.7 小时。

## 5. A/B 验证矩阵

不要继续用单个 33 MB 文件代表整批。固定准备一组约 0.8–1.5 GiB、覆盖真实分布的无敏感样本：

- 100 个 ≤1 MiB 文件；
- 100 个 1–4 MiB 文件；
- 30 个 4–16 MiB 文件；
- 3 个 64–256 MiB 文件；
- 1 个约 1 GiB 文件（可选）。

每组跑 3 次，取中位数：

| 组 | HTTP | host | chunk | 文件并发 | 目的 |
|---|---|---|---:|---:|---|
| A | urllib close | 固定 d.pcs | 4 MiB | 1 | 当前基线 |
| B | Session Keep-Alive | 固定 d.pcs | 4 MiB | 1 | 单独测连接复用 |
| C | Session | locateupload | 4 MiB | 1 | 单独测推荐节点 |
| D | Session | locateupload | 4 MiB | 2 | 文件并发收益 |
| E | Session | locateupload | 4 MiB | 4 | 推荐候选 |
| F | Session | locateupload | 8 MiB | 4 | 测分片大小增量 |
| G | Session | locateupload | 8 MiB | 8 | 只验证饱和点，不作为默认 |

验收指标：

- 0 文件丢失；
- 远端 path 与 size 全部一致；
- 重跑全部 skip；
- 无时间戳重复目录；
- 无明文 Token / dlink 日志；
- 失败率 < 0.5%，失败项重跑可恢复；
- 4 并发吞吐达到 3.2 MB/s 以上，或能用指标明确说明瓶颈仍在网络/PCS。

## 6. 最终建议

1. **不要只实现原报告的 `--chunk-size 8M --concurrency 4`。** 它可能提速，但遗漏连接复用、推荐上传域名和分片重试，也没有针对 75% 小文件优化。
2. 第一提交做 Session、分片重试、指标、locateupload 实验开关。
3. 第二提交做“串行规划 + 文件级并发 4”。
4. 第三提交再加 `fast` profile（8 MiB + concurrency 4 + 更小 delay）。
5. 小文件单步上传独立做兼容性实验，通过才启用。
6. 当前网络下把 **3.2–4.2 MB/s** 视为成功；若想再高，先换网络并重跑 `networkQuality`，不要继续堆并发。
