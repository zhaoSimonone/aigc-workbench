# 容量性能复核

## 目标及方案评审

上一轮消除了首屏全量下载。本轮验证 1 万、3 万素材及高关联密度下的退化风险。
测试数据与生产数据分离，独立 PostgreSQL 容器限制 CPU/内存，生产仅做只读验收。

先记录相同数据、相同资源条件下的基线，再实施有证据支持的改动：

1. 搜索：检查逐行标签聚合的执行次数；优先集合化查询，保留中文子串及 `%/_` 字面量规则。暂不引入外部搜索服务或需要双写维护的搜索缓存。
2. 人物相册：检查重复扫描与分类统计；优先一次分组聚合，保留空相册、固定封面、筛选和用户隔离。
3. 详情与播放：测试标签 × 父关系 × 子关系造成的中间行膨胀；分别聚合关系，播放下载只读必要字段。
4. 前端：限制连续翻页后的 DOM 和关联请求并发，避免数据总量变成浏览器永久驻留量。保持跨页选择、筛选、重试和详情编辑。
5. 统计、深分页和次级库：依据实测决定是否修改；不为尚未出现的规模引入复杂缓存一致性问题。

评审约束：不改变旧全量 API 合约；不省略详情字段；不污染生产数据；不运行生产压测；
部署前完成现有回归和桌面/移动浏览器验收，保存备份与回滚镜像。

## 验证记录

### Review 发现与实施

1. **高关联详情存在乘法放大，必须修复。** 旧查询同时连接标签、父素材、子素材；
   30 个标签 × 100 个父关系 × 100 个子关系产生 30 万行中间结果。
   改成三个独立索引子查询；播放和下载鉴权仅查五个必要字段。
   上传完成后的详情回填也复用新查询，避免遗漏同类路径。
2. **搜索逐素材重复聚合标签，必须修复。** 改成对当前账号标签一次聚合后连接。
   保留跨字段/标签拼接后的中文子串语义、标签顺序和 `%/_/反斜杠` 字面量规则；
   新增 `asset_tags(tag_id,asset_id)` 索引。没有引入易失效的异步搜索副本。
3. **相册重复扫描分类和封面，必须修复。** 统计与分类分别集合聚合，
   相册总数只计算名称集合，避免为计数重复计算所有封面。
4. **深分页计算了跳过素材的标签，必须修复。** 先用物化 CTE 选页内 ID，
   再读取卡片字段和标签。最终 Review 又将页内 CTE 收窄到 ID，
   避免排序携带宽字段。三万条最后一页的标签聚合从执行 30,000 次降至 60 次。
5. **连续加载导致 DOM 无界增长，必须修复。** 保留每次加载 60 条，
   单批最多驻留 180 条；之后“下一批”替换，支持“上一批”。
   网格、相册、关联选择及封面选择共用分页控制。
   批次边界按服务端消耗的 offset 计算，避免并发新增导致去重后边界漂移。
   按 ID 获取关联素材每个 hook 最多两个并发请求，失败可重试。
6. **事务内二次申请池连接可能耗尽连接池，必须修复。** 最后一轮审查发现，
   导入/上传回填详情复用查询时不能再申请新连接；既有素材整理和提示词
   创建/编辑也存在同类调用。改为将已持有的 client 传给查询函数，
   不增加连接池大小来掩盖等待问题。对照运行复现旧代码连接等待超时，
   修复后使用最大连接数为 1 的真实 PostgreSQL 池通过全部写入测试。

审查保留项：

- 摘要与精确总数仍扫描有效数据，但不阻塞首批展示；三万条完整 HTTP
  摘要中位数 191 ms，暂不增加缓存失效体系。精确计数、名称排序和子串搜索
  不是常数复杂度，需要在更大规模继续测量。
- 次级库进入对应页面后加载。复核时生产只有 2 个提示词、21 个账号、
  28 首音乐，不是当前瓶颈；音乐搜索依赖完整关联素材名称，
  直接截断关联数组会改变搜索结果，因此没有以裁剪数据替代正确分页。
- 旧 `/api/assets` 默认全量契约保留，网页主浏览不再调用它。
  外部脚本主动请求全量时仍需承担全库传输成本。

### 测试方法

测试运行在独立 PostgreSQL 和 API 容器，未对生产库造数或压测。
三个账号分别有 1,000 / 10,000 / 30,000 条素材，总计 41,000 条。
每条有约 1.6 KB 备注/JSON 数据和通常 3 个标签；每个账号另有
30 标签、100 父关系、100 子关系的高关联样本，最多 1,000 个相册。
这验证素材数量及关联密度，不等同于 30,000 个不同标签。

数据库限制 0.75 CPU / 384 MiB，API 限制 0.5 CPU / 256 MiB；
PostgreSQL `shared_buffers=64MB`、`work_mem=4MB`。
前后使用相同隔离数据库及资源限制，主机仍运行原业务，存在正常调度波动。
直接查询每项预热后采样 7 次，详情 3 次；不计公网网络和对象存储下载。

### 三万条改造前后

下表为直接调用查询处理函数的中位数，单位毫秒；基线是上一轮首屏分页版。

| --- | ---: | ---: |
| 首批 60 条 | 32.1 | 7.1 |
| 最后一页（offset 29,940） | 1,805.3 | 10.0 |
| 名称排序 | 99.5 | 53.9 |
| 名称搜索 | 2,976.0 | 470.3 |
| 字面量搜索 | 2,872.5 | 438.6 |
| 标签子串搜索 | 2,926.0 | 474.1 |

| 相册列表 | 2,768.7 | 93.7 |
| 高关联详情 | 6,871.4 | 2.4 |

一万条下，首批 5.3 ms、最后一页 6.2 ms、名称搜索 208.4 ms、
相册 32.1 ms、高关联详情 1.8 ms。
摘要 SQL 未改动，三万条直接查询中位数从基线 188.6 ms 波动到 237.2 ms；
最终镜像完整 HTTP 复测为 191 ms。没有将这项未优化的指标包装成性能收益。

`EXPLAIN ANALYZE BUFFERS` 进一步确认：

- 最后一页查询执行时间 1,731.3 → 8.7 ms，标签子计划最多执行
  30,000 → 60 次；最后一页仍需遍历索引，不承诺无限规模的固定耗时。
- 高关联详情 7,008.8 → 0.474 ms，中间结果峰值
  300,000 → 100 行，临时写入 138,252 → 0 个块。
  EXPLAIN 时间是单条 SQL 执行时间，与完整接口时间分开记录。

## 容量结论及边界

已验证的容量是**单账号 30,000 条素材、5 个混合请求并发**，
涵盖大关联详情及最多 1,000 个相册。几千到上万条素材的普通浏览，
不再承担原来的全库下载、逐行聚合、关联乘法放大和无界卡片 DOM。
不能由此推导任意数据分布、任意并发量都无瓶颈。

- 子串搜索和统计仍随数据量增长。后续若超过此验证规模或搜索持续超过
  1 秒，应结合实际执行计划评估搜索索引/投影、游标分页及摘要缓存。
- 数千首音乐、数千提示词、单素材数千关系、数万独立标签不在本次容量验证内；
  对应页面需届时以真实数据分布评估独立分页和渲染成本。
- 高并发导入、转码、海量上传不是本次浏览压测工作负载；
  2 CPU / 约 2 GB 主机仍有有限资源，不能保证后台重任务没有影响。
- OFFSET 翻页不是跨请求快照；并发增删可能改变跨页位置。
  已验证去重、批次边界及返回上一批，但不承诺并发写入下的快照一致性。
- 桌面 Chrome 和手机尺寸 WebKit 为自动化浏览器，并非真实手机弱网测试。
  封面和视频速度仍依赖访问网络及对象存储。
