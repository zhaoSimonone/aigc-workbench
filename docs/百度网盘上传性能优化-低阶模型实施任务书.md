## 0. 任务结论

不要只实现：

```text
--chunk-size 8M --concurrency 4
```

完整目标是：

1. HTTP Keep-Alive / 连接池；
2. 分片级网络重试；
3. 分阶段上传指标；
4. 串行规划远端目录和跳过项；
5. 文件级并发，默认仍为 1，快速档为 4；
6. 可配置 4/8/16/32 MiB 分片；
7. 可选的动态上传域名 `locateupload`，失败安全回退；
8. 保持原有幂等、逐片 MD5、远端 size/path 校验、不删除本地文件。

当前网络通用上行约 5.05 MB/s，百度聚合峰值约 4.05 MB/s。验收目标是把整批有效速度提升到 **3.2–4.2 MB/s**，不是无限增加并发。

## 3. CLI 设计

新增参数：

```text
--profile safe|fast
--chunk-size 4M|8M|16M|32M
--concurrency N
--inter-chunk-delay SECONDS
```

### 3.1 参数默认值

`argparse` 中新参数默认值建议先设为 `None`，解析后再由 profile 填充，这样显式参数可以覆盖 profile。

| profile | chunk size | concurrency | delay | upload host |
|---|---:|---:|---:|---|

## 4. HTTP 传输层

### 4.1 使用 Session

当前 `urllib.request` 每次请求强制 `Connection: close`。上传路径改用支持连接池的客户端。

推荐：

```python
requests.Session
requests.adapters.HTTPAdapter
```

新增：

```text
skills/baidu-netdisk-archive/requirements.txt
```

内容：

```text
requests>=2.31,<3
```

如果环境缺少 `requests`：

- 不要输出 Python traceback
- 给出明确安装命令
- 不要静默回退到无连接池的旧上传实现

只读子命令可以一起迁到新的 transport，也可以暂时保留 urllib；但不要破坏其行为。

### 4.2 Session 生命周期

- `concurrency=1`：一个上传 Session 贯穿整个批次
- `concurrency>1`：使用 `threading.local()`，每个 worker 线程一个 Session
- 不在多个线程间共享同一个 Session
- 每个 Session 的 adapter pool size 不小于 2
- 批次结束关闭所有可追踪 Session；若 thread-local 不便统一关闭，至少保证进程退出可回收

推荐默认 Header：

```text
User-Agent: pan.baidu.com
```

### 4.3 Timeout

区分控制请求和数据请求：

```text
control timeout: connect 10s, read 60s
chunk timeout:   connect 10s, read 180s
```

不要使用无限 timeout。

### 4.4 敏感信息

百度 Token 在 query 中，因此：

- 禁止记录完整 URL
- 禁止直接把 `requests.RequestException` 的字符串写入日志，因为其中可能包含 URL
- 错误日志只保留：host、API 名、HTTP status、errno、attempt
- 实现 `redact_url()` / `safe_http_error()` 或同等集中去敏逻辑
- 测试必须断言错误文本里没有假 Token

## 6. 分片大小参数化

把全局 `BLOCK_SIZE` 改为配置值，但保留常量默认：

```python
DEFAULT_BLOCK_SIZE = 4 * 1024 * 1024
```

下列函数接收 `chunk_size`，不要偷偷继续读全局：

- `block_digests(path, chunk_size)`
- 分片读取/offset 计算
- `upload_file(...)`
- 任何 benchmark/metrics 逻辑

`md5_of()` 如果未使用，可以保留但也要支持显式 buffer size；不要顺手删除导致其他调用者出错。

### 6.1 分片大小超限

若服务端返回明确的分片大小超限（例如 31364）：

- `safe`：直接报清晰错误
- `fast`/显式 >4 MiB：允许对该文件回退到 4 MiB
- 回退必须：重新计算完整 block list → 重新 precreate → 新 uploadid → 从头执行该文件
- 最多回退一次，禁止无限递归
- metrics 标记 `chunkFallbackFrom` / `chunkFallbackTo`

不要在旧 uploadid 下把 8 MiB 临时切成两片 4 MiB。

## 7. 分片级重试

新建类似：

```python
upload_block_with_retry(
    token,
    upload_host,
    remote_path,
    uploadid,
    partseq,
    data,
    expected_md5,
    session,
    max_attempts=4,
)
```

### 7.1 哪些情况重试

- connect/read timeout
- connection reset / TLS 临时错误
- HTTP 408 / 429 / 500–599
- 百度返回已有 `RETRYABLE` errno
- 返回非 JSON
- 服务端回显 MD5 与本地不一致：允许重试，但每次都必须重新发完整分片

### 7.2 哪些情况不重试

- Token 失效
- 权限错误
- 路径非法
- 分片大小超限（进入 §6.1 回退流程）
- 明确的参数错误

### 7.3 退避

建议：

```text
1s, 2s, 4s，加 0–250ms jitter
```

固定 `inter_chunk_delay` 发生在一个分片最终成功后；重试退避与它分开。

### 7.4 文件读取

每个 worker 独立打开文件。支持两种安全实现：

- `seek(offset)` + `read(chunk_size)`，每个 worker 自己的 file handle
- `os.pread(fd, size, offset)`

不要多个线程共享同一个 file object。

## 8. 动态上传域名

### 8.1 模式

- `fixed`：保持当前 `d.pcs.baidu.com`
- `auto`：尝试 locateupload，失败警告后回退 fixed
- `required`：locateupload 失败则该文件失败，不回退

### 8.2 locateupload 请求

预上传拿到 `uploadid` 后调用：

```text
GET https://d.pcs.baidu.com/rest/2.0/pcs/file
```

参数：

```text
method=locateupload
appid=250528
access_token=<TOKEN>
path=<当前真实 remote_path>
uploadid=<UPLOAD_ID>
upload_version=2.0
```

解析 HTTPS 候选顺序建议：

1. `servers[].server`
2. 字符串形式的 `server`
3. `host`（补 `https://`）
4. 无候选时按 mode 回退/失败

第一版不使用 QUIC host。

### 8.3 兼容旧上传契约

当前代码分片请求的 `path` 是：

```text
/apps/BaiduPCS/<uploadid>
```

这与当前公开文档的“传真实 path”不同，但旧链路已实测可用。不得直接全量替换。

实现策略：

- `fixed` 模式保持旧 query path，确保默认兼容
- locateupload 成功的 `auto/required` 模式使用真实 `remote_path`
- 将 query path 模式记录进 metrics（`legacy` / `remote`）
- 单元测试覆盖两种模式

不要同时迁移 `/api/precreate`、`/api/create` 到新版 xpan 接口。本轮只做 upload host 实验能力。

## 9. 利用 precreate 的缺失分片列表

兼容两种契约：

- 旧接口秒传：`return_1 == 0`
- 新接口风格秒传：`return_type == 2`

分片选择：

1. 如果响应中存在**非空且全部为合法整数**的 `block_list`，只上传这些索引
2. 如果 `block_list` 缺失、为空或格式不合法，安全回退为上传全部分片
3. 索引必须在 `[0, len(digests))`
4. 不要相信越界值

创建文件时仍提交完整、按原始顺序排列的 digest 列表。

metrics 区分：

```text
chunksTotal
chunksRequested
chunksUploaded
```

## 10. 串行规划阶段

在启动线程池之前完成规划，避免目录创建竞态。

### 10.1 规划步骤

1. `collect()` 本地文件
2. 计算所有远端父目录集合
3. 按路径深度和名称排序，串行 `ensure_dirs()`
4. 每个远端父目录只调用一次 `list_dir()`
5. 形成 `UploadPlanItem`：
   - local_path
   - relative_path
   - remote_path
   - size
   - action: `skip | upload | replace`
   - existing_size
6. skip 项直接进入结果，不提交线程池
7. upload/replace 项提交线程池

### 10.2 `--force` 修复

当前实现的 `--force` 没有先删除远端同名文件，与 Skill 文档“先删旧版本再上传”不一致。

本任务一并修复：

- 远端存在，且 `--force`：plan action=`replace`
- 远端存在、size 不同、未 force：action=`replace`
- worker 上传前删除旧文件
- 删除失败则该文件失败，不继续 precreate

### 10.3 规划副作用

普通上传模式的规划可以创建缺失目录，这是原有行为。

但：

- 参数校验必须在创建目录之前
- `--dry-run` 禁止创建目录、删除文件、precreate
- dry-run 可只展示本地计划；不要为了判断 skip 而要求写接口

## 11. 文件级并发

### 11.1 模型

```python
ThreadPoolExecutor(max_workers=concurrency)
```

- 一个 future 对应一个文件
- 单文件内部串行分片
- 主线程收集 future、更新 results、打印进度和写 metrics
- worker 不直接修改共享 `results`
- worker 不修改共享 `remote_cache`

### 11.2 输出

主线程打印：

```text
[完成 12/100 | 上传中 4] relative/path.mp4 -> 已上传 ...
```

完成顺序可以与文件顺序不同，但最终失败明细应按原始 relative path 排序，便于重跑定位。

### 11.3 中断

- 捕获 Ctrl-C
- 设置 `threading.Event`
- 停止提交新 future
- 取消未开始 future
- worker 在文件阶段之间、分片之间检查 event
- 已经进入 HTTP 请求的任务可等 timeout 返回
- 退出码 130
- 已完成文件保持不变
- 不删除本地文件

### 11.4 并发上限

- CLI 最大 8
- 不做嵌套分片并发
- `fast` 默认 4
- 不要因为机器线程多自动增大

## 19. 高阶 Review 检查点

后续 Review 会重点检查：

- 默认无参数是否真的保持旧行为
- requests 异常是否泄漏 access_token URL
- Session 是否真正在线程内复用
- 是否意外形成“文件并发 × 分片并发”
- ensure_dirs 是否仍可能并发创建重复目录
- precreate block_list 为空时有没有误判为“不用上传”
- create 是否提交完整且有序的 digest
- chunk fallback 是否重新 precreate
- Ctrl-C 是否会继续大量提交任务
- metrics 是否线程安全、是否泄密
- `--force` 是否真的先删旧文件
- read-only 子命令是否回归
- 低阶模型是否偷偷进行了真实上传/删除
